# Что сделать для сдачи на «3»

## 1. Перенесите файлы

Сделайте резервную копию своей папки guestbook-workshop.
Скопируйте содержимое этого проекта в неё с заменой одноимённых файлов.
Обязательно перенесите `.github/workflows/ci.yml`, `tests/` и файлы с точкой
в начале имени. `.venv` переносить не нужно.

Локальный `.env` в архив не входит. Сохраните свой существующий `.env`.
Убедитесь, что в нём есть POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB,
соответствующие вашей базе. Для нового запуска создайте .env из .env.example,
как указано в README.

Файл блокировки должен называться ровно `uv.lock`, без `(2)`.
В архиве он уже так называется. Старые копии uv(1).lock/uv(2).lock не нужны.
README теперь содержит инструкцию, а не копию кода main.py.

## 2. Проверьте запуск

Запустите Docker Desktop. В терминале PowerShell в папке проекта выполните:

```powershell
docker compose up --build -d --wait
docker compose ps
```

Откройте http://localhost:8000/docs. Отправьте POST /messages и получите
тот же текст через GET /messages. Команды остановки и повторного запуска
есть в README. Если порт 8000 занят, остановите прежний экземпляр сервиса.

## 3. Отправьте проект на GitHub

Если репозитория ещё нет, создайте пустой GitHub-репозиторий, например
`guestbook-workshop`, без автоматически созданных README и .gitignore.
В терминале в папке проекта:

```powershell
git init
git branch -M main
git add .
git status
```

Перед коммитом убедитесь, что `.env` и `.venv` отсутствуют в staged files.
Проверка:

```powershell
git ls-files .env
git check-ignore .env
```

Первая команда не должна ничего вывести, вторая должна вывести `.env`.
Если .env уже отслеживался, выполните `git rm --cached .env` перед коммитом.
Это убирает файл из новых коммитов, но не из старой истории. Если рабочие
секреты уже были опубликованы, замените их и очистите историю перед сдачей.

Затем:

```powershell
git commit -m "Add CI, tests and container image publishing"
git remote add origin https://github.com/YOUR_LOGIN/guestbook-workshop.git
git push -u origin main
```

В URL замените YOUR_LOGIN своим логином. При первом push Git может попросить
авторизацию в GitHub. Если репозиторий уже существует и origin настроен,
повторно `git init` и `git remote add` не нужны: используйте его текущий origin.
Проверьте его командой `git remote -v`, затем выполните add, commit и push.

## 4. Дождитесь результата

На GitHub откройте репозиторий → Actions → CI and image.
Должны стать зелёными обе job: `check` и `publish`. В Packages у владельца
репозитория найдите образ с тегом `latest`. До реального push работа Actions
и публикация образа не подтверждены.

Если check упал, откройте красный шаг и прочитайте ошибку; publish при этом
не запускается. Если publish сообщает permission denied, проверьте разрешения
Actions/Packages в настройках репозитория и ограничения организации.

Чтобы показать запуск именно опубликованного образа, выполните команды
из раздела «CI и образ» в README, затем снова проверьте /docs и /messages.

## 5. Что показать преподавателю

1. Репозиторий с Dockerfile, compose.yaml, uv.lock и .env.example.
2. Успешный запуск Compose и работу POST/GET сообщений через /docs.
3. Зелёный workflow в Actions: Ruff, 6 тестов и публикация образа.
4. Образ latest в Packages.
5. README с командами запуска и остановки.

Объяснение своими словами:

«Приложение и PostgreSQL запускаются через Compose. Приложение ждёт готовности
базы, а данные сохраняются в volume. Настройки передаются через окружение,
.env не попадает в Git и образ. На push и pull request CI запускает Ruff и
pytest с отдельной PostgreSQL. После зелёного check push в main публикует
образ latest в GHCR. Запуск образа выполняется вручную. Релизы по semver реализованы через git-теги и версионные образы;
откат ещё не демонстрировался».

Проект расширен релизами по тегам сверх исходного объёма для «3»: контейнеризация и CI реализованы,
но откат ещё не продемонстрирован. Оценка остаётся за преподавателем.
Не утверждайте, что у вас настроен живой прод или автоматический деплой на сервер:
в этом варианте их нет. Если преподаватель требует сервер даже для «3»,
потребуется отдельно развернуть этот Compose на предоставленном Linux-хосте.

## Что проверено при подготовке

- Установка зависимостей через uv и согласованность lock-файла.
- Ruff: успешно.
- Три теста без PostgreSQL: успешно.
- Три теста с PostgreSQL: подготовлены для Actions, здесь не запускались.
- Docker-сборка и GitHub Actions: здесь не запускались; результат проверяется
  после локального запуска и push. В среде подготовки нет Docker/PostgreSQL.


с тегом v0.1.0, а также CHANGELOG.md. Если v0.1.0 уже существует,
используйте следующую версию и обновите changelog. Подробнее — в README.
